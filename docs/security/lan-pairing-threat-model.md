# Local pairing threat model

Status: implementation design, **independent security review pending**. Issue [#8](https://github.com/murilaiooo/openvista/issues/8) and G-08/G-06 remain open. `PairingSecurity.REVIEWED` is a compile-time `false` gate. The public coordinator returns a review-pending explanation before enumerating interfaces or creating a socket. Writing this document does not approve that gate.

## Trust boundaries

The owner starts pairing on the TV. The phone, browser, Wi-Fi network, other LAN clients, submitted text and HTTP framing are untrusted. A QR fragment carries a random 256-bit session key and independent 128-bit session ID for two minutes. The protocol accepts one encrypted URL, title and explicit HLS/DASH choice. The TV shows a pending request; only a subsequent TV approval returns that source to the library UI. Pairing does not fetch the source, start playback, import lists, change settings or write the library itself.

**The browser workflow remains unavailable.** The current listener is HTTP; the phone page keeps its form hidden and disabled unless loaded through HTTPS with secure-context WebCrypto. It clears the fragment and reports failure on HTTP before accepting source entry. No plaintext transfer or insecure JavaScript crypto fallback exists. A working authenticated browser bootstrap is still required before enablement; implementing authenticated envelopes alone does not satisfy that requirement.

The listener binds one unambiguous RFC1918 IPv4 interface and an ephemeral port, never a wildcard interface. Ambiguous/no private addresses fail closed. Peers must belong to that interface's subnet. There is no discovery broadcast, cloud relay, account, persistent pairing, port forwarding or automatic startup. TV screen closure, denial, approval, expiry and coordinator closure end the socket session and wipe the raw key buffer. The worker checks the bound address/prefix before accepting and serving requests and stops when it disappears. Reconnect requires a fresh TV action. Key erasure is best effort: JVM/browser strings and crypto-provider copies cannot be guaranteed erased.

## Threats and controls

| Threat | Implemented boundary | Remaining review work |
| --- | --- | --- |
| Guessing/replay | SecureRandom 32-byte AES key, independent session ID, 128-bit GCM authentication tag, monotonic two-minute expiry, single valid submission, random request ID and one TV approval | Inspect entropy, WebCrypto/JCA interoperability, IV uniqueness and race behavior; exercise stale queued callbacks and approval at expiry |
| CSRF and DNS rebinding | Exact numeric Host plus port, exact Origin on POST, JSON, no OPTIONS/CORS response, no cookies or bearer header; QR key stays in a fragment removed from visible history | Browser matrix and hostile-origin cases; a future HTTPS listener must update the exact origin check with its reviewed transport |
| Unauthorized library writes | Parser validates URL/kind; incoming request remains in memory and requires TV approval; only `approve(id)` returns accepted data | Inspect every caller to ensure it mutates only after approval and previews without exposing URL credentials |
| SSRF and executable input | UserSourceParser, bounded URL/title/JSON, no URL requests during pairing, no HTML insertion from submitted input | Playback has a separate user-source network boundary; pairing is not proof of safe playback |
| Slow clients and memory exhaustion | One client at a time, backlog 2, 1.5-second socket timeout, two-second request deadline, 8 KiB headers, 8.5 KiB encrypted envelope, 6 KiB decrypted body, at most 24 connections per session; phone response capped at 512 bytes with a five-second abort | Fuzz HTTP framing and run abuse cases on target hardware; LAN peers can still exhaust the small connection budget |
| XSS, remote assets and token leakage | App-generated page, escaped localized labels, nonce CSP, no external assets, no URL/referrer token, no-store, no-referrer, frame denial, no logs/persistence | Browser history, keyboard/browser autofill and phone screenshot behavior remain outside TV control |
| Interface exposure | Private IPv4 binding, subnet restriction, no listener while gate is false, explicit TV start and bounded lifetime | Inspect VPN/hotspot/guest network topology and client-isolation behavior |
| LAN interception | Source and acknowledgement use AES-256-GCM; no plaintext source endpoint or transmitted bearer key; HTTP page refuses source entry | **Unresolved active-attacker bootstrap:** HTTP-delivered JavaScript can be replaced to steal the QR fragment or user input. Ordinary LAN HTTP also lacks WebCrypto. A trusted HTTPS origin/certificate provisioning scheme or separately authenticated native phone client must be implemented and reviewed before enablement |

## Encrypted envelope contract

The QR fragment is `v1.<base64url session ID>.<base64url AES key>`, without padding. POST `/source` accepts only JSON fields `v`, `sid`, `iv` and `ciphertext`. Version is integer `1`; the session ID must match. A 12-byte random IV and a 128-bit GCM tag protect the UTF-8 source object. Ciphertext includes the appended authentication tag. Canonical unpadded base64url and byte limits are checked before decryption. Android uses its standard `AES/GCM/NoPadding` provider; the browser uses nonextractable WebCrypto AES-GCM keys. No crypto package or third-party script is added.

Additional authenticated data is the UTF-8 string `OpenVista pairing v1\n<session ID>\n<numeric host:port>\nsource`. The response uses a fresh random IV, the same fields/key, direction `ack` and exact plaintext `pending-tv-approval`. The phone authenticates that acknowledgement before displaying a pending status. It does not imply TV approval, library insertion or playback. Direction, authority and session binding prevent cross-endpoint, cross-session and reflection reuse. The first valid source consumes the listener; another attempt requires a new TV session and key. The phone aborts and clears its form on expiry, page exit, backgrounding or failure, with no automatic resubmission.

The [Web Cryptography specification](https://www.w3.org/TR/webcrypto/) restricts SubtleCrypto to secure contexts and defines AES-GCM IV, additional-data and tag parameters. Android's [GCMParameterSpec](https://developer.android.com/reference/javax/crypto/spec/GCMParameterSpec) is available before the API-28 target. These are platform APIs; this implementation adds no external cryptography dependency or licensing obligation. These references describe the APIs, not a review or interoperability result for this protocol.

The HTTP scheme does not provide TLS protection; the [HTTP semantics standard](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.2.1) defines its origin semantics separately from HTTPS. Browser CORS controls do not protect against a malicious native LAN client; see the [Fetch CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol). Binding and backlog limit follow [ServerSocket.bind](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/net/ServerSocket.html#bind(java.net.SocketAddress,int)); backlog is an implementation-dependent hint, so application time/body/session bounds remain necessary.

## Enablement record required

An independent reviewer must record name/date, reviewed commit, findings and fixes, residual risks and owner decision. Include protocol abuse cases, browser behavior, target Fire OS listener lifecycle, network switching and background shutdown. Implement and review trusted phone-client bootstrap before changing the compile gate; a certificate-warning bypass, treating a private IP as secure, or downloading crypto JavaScript over HTTP is not a solution. Any HTTPS implementation must align listener, QR scheme, certificate trust and exact Origin checks. Permission/platform behavior on newer Android versions needs a separate check. No build, browser execution, crypto-vector test, device check or security acceptance was performed for this implementation.
